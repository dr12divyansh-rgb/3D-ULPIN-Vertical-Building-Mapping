# LOD1 → LOD2 Dataset Architecture

This document describes the **PLATEAU-inspired LOD1 → LOD2 building-generation
workflow** added in Step 2, on top of the Step 1 synthetic LiDAR pipeline.

> **PLATEAU attribution.** PLATEAU is Japan's national 3D city model project
> (https://www.mlit.go.jp/plateau/). This project adopts the *conceptual*
> architecture of PLATEAU's CityGML levels of detail (LOD1 block models, LOD2
> detailed buildings with semantic surfaces). **No PLATEAU code, schemas, or
> datasets are copied.** All geometry here is procedurally generated by our own
> Blender-based generator, and all data is synthetic.

---

## 1. Conceptual model

For every synthetic building we produce three distinct representations:

```text
Original Blender geometry (source of truth)
        │
        ├──→ LOD1               simple reference block
        │
        ├──→ Ground-truth LOD2  detailed external geometry (reconstruction target)
        │
        └──→ Synthetic LiDAR    observed, noisy/incomplete point cloud
```

The future reconstruction system will try to go from the *observed* side
(`LOD1 + LiDAR`) to a *predicted LOD2*, and will be evaluated against the
ground-truth LOD2. This step only produces the ground truth; nothing predicts
LOD2 yet.

## 2. What LOD1 means here

LOD1 is a **flat-top extrusion of the footprint** to the eave (wall) height:

```text
2D footprint  ──extrude──▶  LOD1 block model
```

- No roof geometry, no parapet, no floor markers.
- Height = `wall_height` (sum of floor heights).
- `ground_elevation` = 0.0 (no terrain), `base_z` = 0.0, `top_z` = `height`.
- Always **watertight** (a closed extrusion, including the ground face).
- For courtyard footprints the extrusion is a true annulus (outer walls +
  courtyard walls + annular top/bottom).

## 3. What LOD2 means here

LOD2 is the **detailed external building geometry** with *semantic surfaces*:

```text
WallSurface   — vertical wall faces (including gable/shed end walls)
RoofSurface   — roof planes (flat top, gable/hip slopes, shed slope)
GroundSurface — ground-contact face
```

- Correct total height (`wall_height` + roof rise).
- Actual footprint, roof type (`flat` / `gable` / `hip` / `shed`).
- Structured: every face carries exactly one surface type — it is **not** an
  anonymous triangle soup.
- Watertight where appropriate (all our LOD2 meshes are watertight).
- For a **flat roof**, LOD2 is geometrically similar to LOD1 (same height) —
  this is intentional; we do not invent roof complexity that is not there.

## 4. How LOD1 is generated

`blender/building.py` builds LOD1 from the exact same footprint + eave height
used for the detailed building:

```text
footprint (outer ring, + hole ring for courtyard)
      + eave height
      → walls + flat top + ground face   (all watertight)
```

The mesh is transformed to the building's world position/rotation, then
exported as a group-tagged OBJ (`lod1/building_XXXXXX.obj`) plus metadata.

## 5. How ground-truth LOD2 is generated

LOD2 is built from the **original Blender geometry**, never from the LiDAR:

```text
footprint walls (0 → eave height)
      + roof surfaces (flat / gable / hip / shed, tagged Roof/Wall)
      + ground face
      → structured SurfaceMesh
```

Surfaces are tagged on Blender bmesh faces via a custom face layer
(`semantic`) and exported as a group-tagged OBJ with per-surface-type `g`
groups, plus a structured `metadata.json` (face counts + areas per surface).

## 6. How LiDAR relates to both

The synthetic LiDAR is sampled from the same Blender scene geometry:

- Points carry `x, y, z, class, building_id`.
- Building points come from the building's *wall + roof* surfaces (the hidden
  ground-contact face is excluded so it does not duplicate scene-ground points).
- Optional **floor marker** slabs (config `building.floor_markers`) are emitted
  only into the LiDAR sampling geometry — they make floors visible in the
  point cloud but are **not** part of the clean LOD2 ground truth.
- Noise / dropout / occlusion / variable density (config `lidar.*`) apply only
  to the LiDAR, never to LOD1/LOD2.

```text
Ground truth:  original Blender geometry ──▶ LOD2  (clean)
Observed:      original Blender geometry ──▶ LiDAR (noisy / incomplete)
```

## 7. Why LOD2 is not derived from the LiDAR

The whole purpose of the dataset is to compare a future *reconstruction*
against a known ground truth. If LOD2 were derived from the noisy LiDAR, the
"ground truth" would contain the same errors the reconstruction is expected to
fix, and evaluation would be meaningless. Therefore LOD2 always comes from the
exact procedural parameters / Blender geometry, and LiDAR is an independent
degraded observation of that same geometry.

## 8. Where future AI segmentation fits

```text
LOD1 + LiDAR
      ↓
PointCloudSegmenter.predict(...)     (PointNet++ / RandLA-Net — future)
      ↓
segmented building points
      ↓
deterministic geometry logic         (reconstruct structured surfaces)
      ↓
predicted LOD2
      ↓
evaluate_lod2(predicted, ground_truth)
```

The design principle (PLATEAU-inspired): the AI will *interpret/classify* the
measured data; **deterministic geometry logic** constructs the structured LOD2.
We do **not** intend the AI to emit an arbitrary mesh directly.

A placeholder interface exists in `core/segmentation.py`:

```python
class PointCloudSegmenter:
    def predict(self, point_cloud): ...
```

and evaluation utilities exist in `core/evaluation.py`
(`evaluate_lod2(pred, gt)`, `is_sane(...)`) plus the CLI
`scripts/evaluate_lod2.py`.

## 9. PLATEAU-inspired concepts adopted

- LOD1 as a simple block model from footprint + height.
- LOD2 as a detailed building with **semantic surfaces** (Wall / Roof / Ground).
- Structured, semantically-typed surfaces rather than triangle soups.
- Ground truth kept separate from observation.
- Topology validation (watertight, no non-manifold edges, no zero-area faces).

## 10. What is intentionally NOT copied from PLATEAU

- No PLATEAU code, CityGML schemas, sample data, or styles.
- No CityGML export yet (kept as a clean future interface).
- No real government/building data ingestion.

## 11. Dataset structure (per scene)

```text
scene_XXXXX/
├── lod1/
│   ├── building_XXXXXX.obj      # LOD1 geometry (g-tagged OBJ)
│   └── metadata.json            # per-building LOD1 metadata
├── lidar/
│   ├── pointcloud.ply           # synthetic LiDAR (x,y,z,class,building_id,…)
│   └── metadata.json            # lidar params + point counts
├── ground_truth/
│   ├── lod2/
│   │   ├── building_XXXXXX.obj  # ground-truth LOD2 geometry
│   │   └── metadata.json        # LOD2 metadata + lod_comparison
│   └── building.json            # full building ground truth (all parameters)
└── scene.json                   # scene summary (id, split, seed, counts)
```

The split is unchanged from Step 1: by **scene**, no building id in more than
one split, test scenes from an independent seed stream.

## 12. LOD comparison metadata

Stored per building in `ground_truth/lod2/metadata.json` and computed from the
actual geometry (not fabricated):

```json
"lod_comparison": {
  "footprint_area_lod1": 158.89,
  "footprint_area_lod2": 158.89,
  "height_lod1": 16.73,
  "height_lod2": 24.24,
  "roof_type": "shed"
}
```

Note: `footprint_area_lod1 == footprint_area_lod2` by construction (no roof
overhangs are modelled); the meaningful differences are height and roof type.

## 13. Commands

```bash
# generate
python synthetic_city/scripts/generate_dataset.py
python synthetic_city/scripts/generate_dataset.py --config synthetic_city/config/small.yaml

# validate (LOD1/LOD2 geometry + point cloud + split)
python synthetic_city/scripts/validate_dataset.py

# visual comparison of LOD1 / LOD2 / LiDAR for one building
python synthetic_city/scripts/compare_building.py --scene <scene_dir> --building <id>
python synthetic_city/scripts/compare_building.py --scene <scene_dir> --building <id> --save out.png

# evaluation (GT vs itself as sanity; or predicted vs GT)
python synthetic_city/scripts/evaluate_lod2.py --scene <scene_dir> --building <id>
python synthetic_city/scripts/evaluate_lod2.py --pred pred.obj --gt gt.obj

# point cloud viewer (Step 1, updated paths)
python synthetic_city/scripts/view_pointcloud.py --input <scene_dir>
```

## 14. Current limitations

- Synthetic data only; not a substitute for a real LiDAR survey.
- `intensity` / `return_number` are placeholders.
- Roof types `gable` / `hip` / `shed` are only generated for rectangle
  footprints; L/T/courtyard/irregular buildings get flat roofs.
- Footprint area is identical between LOD1 and LOD2 (no roof overhangs).
- Self-intersection detection is limited to non-manifold-edge counting; full
  triangle–triangle intersection testing is not implemented.
- Footprint IoU in `evaluation.py` uses a rasterised convex-hull projection
  (an approximation, exact for the GT-vs-GT sanity check).
- Floor markers and parapet-level facade detail are LiDAR-only, not LOD2.
