## 1. What This Project Is

**SIH 26011** (Smart India Hackathon problem 26011): a synthetic building + LiDAR dataset generation pipeline for the **ULPIN** (Unique Land Parcel Identification Number) problem — 3D building reconstruction and semantic segmentation leading to building-level vertical cadastral mapping.

The full target pipeline is:  
RGB imagery → photogrammetry → point cloud → segmentation → LOD2 reconstruction → ULPIN output

Only the **synthetic data generation + ML baseline** are implemented. Everything else is future work.

**LiDAR simulation:**
- Base density: 40 pts/m², variable (0.5–1.5× multiplier per point)
- Class multipliers: ground 0.35×, road 0.5×, building 1.2×, vegetation 2.0×, vehicle 2.0×
- Max 600,000 pts/scene; noise std 0.03 m; 5% dropout
- PLY fields: `x y z class_id building_id r g b intensity return_number`
- `intensity` and `return_number` are **synthetic placeholders** — do not use as model features
- Occlusion simulation is **disabled** (`occlusion: false` in default.yaml)

## 6. ML Pipeline (Step 3 — Experiment 001)

### Model: PointNet++ (`ml/src/models/pointnet2.py`)

- 264,006 parameters; pure PyTorch; CPU-compatible
- Input: `(B, N, 3)` XYZ only (no intensity, no return_number)
- Output: `(B, N, 6)` per-point logits
- 2 Set-Abstraction layers → 2 Feature-Propagation layers

| Layer | npoint | radius | nsample | MLP |
|-------|--------|--------|---------|-----|
| SA1 | 512 | 0.2 | 32 | [64, 64, 128] |
| SA2 | 128 | 0.4 | 32 | [128, 128, 256] |
| FP2 | — | — | — | [256, 128] |
| FP1 | — | — | — | [128, 128, 128] |

### Training config (`ml/config/segmentation.yaml`)

- Chunk size: 4096 points; 24 chunks/train scene, 16 chunks/val scene
- Epochs: 25; batch size: 4; LR: 0.001; weight decay: 0.0001
- Loss: cross-entropy (unweighted — `class_weighted_loss: false`)
- Early stopping patience: 15 epochs; saves best val mIoU checkpoint
- `num_workers: 0` (CPU-friendly, deterministic)
- `device: "auto"` (CPU on this machine)

## 11. Known Issues and Weaknesses

1. **Vehicle (4) and Other (5) classes score 0.0 IoU on test.** These are rare in the synthetic scenes. The model predicts 0 for both. `class_weighted_loss` exists in config but is off; enabling it would help rare classes but could reduce building IoU (the primary metric).

2. **Road class is weak** (IoU 0.149 on test). Road geometry in urban scenes is thin and surrounded by building points; the model conflates road with ground.

3. **mIoU (0.351) is dominated by building (0.914)**. The mIoU metric is misleading for this project — building IoU is what matters for cadastral use.

4. **No novel building styles in test set.** All 18 test buildings use footprint+roof combinations seen in training (8 unique combinations seen during training, 8 seen in test). True generalization to unseen styles has not been measured.

5. **Small dataset.** 7 training scenes / 116 buildings. The model plateaued at epoch 10; adding more scenes may improve rare-class performance.

6. **Validation mIoU is noisy** (oscillates 0.23–0.334 across epochs). This is expected with CPU batch_size=4 and small validation set, but makes early-stopping sensitive to epoch choice.

7. **Occlusion disabled.** The LiDAR simulation is idealized (all surfaces visible). Real-world LiDAR would have significant occlusion.

8. **Floor markers in PLY are indistinguishable from facade points.** They are class=building. This is intentional (realistic facade detail), but means they provide no signal distinguishable from other building points.

## 12. Planned Next Steps

In priority order for the competition:

1. **Step 4: LOD2 geometry reconstruction** — take the PointNet++ building point mask and reconstruct an LOD2 mesh (alpha-shape, Poisson surface reconstruction, or extrusion from predicted floor planes). This is the **critical missing piece** and the goal of the whole pipeline.

2. **Improve rare-class segmentation** — either enable `class_weighted_loss` or use focal loss; add more training scenes with denser vehicle/road coverage.

3. **Evaluate on novel building styles** — generate a secondary test set with unseen footprint+roof combinations (e.g., `L + hip` — never seen in training) to measure real generalization.

4. **Larger dataset** — regenerate with more scenes (`train_scenes: 15+`) to give the model more building diversity.

5. **RandLA-Net** — alternative backbone with random sampling (faster, may generalize better to large outdoor scenes).

6. **Real-world data pipeline** — photogrammetry (Metashape / OpenMVG + OpenMVS) producing a real point cloud, then inference with the trained model.

7. **ULPIN integration** — output format mapping LOD2 building footprints to ULPIN parcel IDs.

8. **CityGML export** — standard format for cadastral 3D city models.

These must not be changed without understanding the downstream impact:

| Constraint | Why |
|-----------|-----|
| `CLASS_IDS` in `labels.py` (ground=0, building=1, …) | Fixed across all generated PLYs, the trained checkpoint, and the viewer. Changing breaks everything. The ML loader verifies this at startup. |
| `seed: 26011` in `default.yaml` | Competition problem number; also used in trained checkpoint, all manifests, and `test_metrics.json`. Change only if intentionally regenerating everything. |
| Test seed offset `1000000` (→ seed 1026015) | Ensures test buildings are truly unseen. Do not use the same seed stream for test as train/val. |
| `intensity` and `return_number` PLY fields are synthetic | Never use as model input features — they are placeholders, not real sensor data. |
| Blender 4.2 LTS | The Blender Python API is version-specific. 4.2 LTS is what the scripts target. |
| Python 3.12 | open3d has no cp313 wheels. Do not upgrade to Python 3.13. |
| `viewer/vendor/three.module.js` is Three.js r160 | Vendored offline. Do not update without testing the viewer — the module API changes between r160 and newer releases. |
| `ml/data/synthetic/` is gitignored | This is intentional — data is regenerated from scripts. The checkpoint is NOT gitignored and must be separately preserved. |
